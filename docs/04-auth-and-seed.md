# 04 — المصادقة وحساب bomba (super_bomba)

## الـ Seed (القسم 6 من الخطة — حرفيًا)

يُحقن الحساب عند **أول تشغيل فقط**، ولا توجد أي بيانات قبله:

| البند | القيمة |
|---|---|
| User | `username = "bomba"` · `level = 900` · `is_system = true` · `is_active = true` |
| Credentials | كلمة المرور `bomba000` — نص تجريبي في الـ Mock فقط مع تعليق صريح في الكود (`services/mock/seed.ts`) |
| Phones | `01281130712` (is_primary = true) · `01281130713` (is_primary = false) |
| Emails | `bomba000@bomba.com` (is_primary = true) · `bomba001@bomba.com` (is_primary = false) |
| Attachments | أفاتار دائري افتراضي بحرف `B` مع `is_primary = true` |

> 🔐 **التشفير الحقيقي (bcrypt) بيتطبق في الباك إند فقط** — ممنوع منعًا باتًا يترك hash أو كلمة مرور في الفرونت.

## شاشة تسجيل الدخول (القسم 7)

1. **حقل واحد** بيقبل اسم مستخدم أو بريد أو موبايل — `SmartIdentifierInput` بيكشف النوع أثناء الكتابة ويعرض Badge (Email / Phone / Username) وأيقونة ملونة ورسالة تحقق حية — بنفس ريجيكسات ملف التصميم المرجعي:
   - بريد: `^[^\s@]+@[^\s@]+\.[^\s@]+$`
   - موبايل مصري: `^(\+?20|0)?1[0125]\d{8}$`
   - اسم مستخدم: `^[a-zA-Z0-9_.-]{3,24}$`
2. كلمة المرور حقل منفصل مع زر إظهار/إخفاء.
3. النموذج متحقق منه بـ **Zod** (`schemas/auth.ts`) + **VeeValidate**، ورسائل الخطأ مفاتيح ترجمة بتترجم حسب اللغة.
4. **عند النجاح:** المسار الإلزامي:
   ```
   /auth/sign-in → (بدون شروط؟) /terms → (بدون إعداد؟) /onboarding → /dashboard
   ```
5. الـ Mock بيتحقق من القيمة المدخلة مقابل الـ seed ويرجّع DTO مثل الباك إند الحقيقي (`AuthResponse`).

**جرّب بنجاح بأي من:** `bomba` أو `bomba000@bomba.com` أو `bomba001@bomba.com` أو `01281130712` أو `01281130713` + كلمة المرور `bomba000`. وأي قيمة تانية بترجع «المعرّف أو كلمة المرور غير صحيحة».

## منطق صلاحيات super_bomba

| القاعدة | التنفيذ |
|---|---|
| 1. أول شرط تحقق (Middleware) | `auth.global.ts` بيفحص `isSuperBomba(user)` **أول حاجة**، وكمان `middleware/super-bomba.ts` named middleware أول واحد في صفحات النظام → `ALLOW_ALL` قبل أي فحص آخر |
| 2. تجاوز النطاقات | `utils/permissions.ts#hasScope()` بيرجّع true فورًا للمستوى 900 (تجاوز tenant_id والـ Self/Tenant Scopes) — الفحص الحقيقي في الباك إند |
| 3. منح الصلاحيات | مشروط في الباك إند إنشاء حسابات مشرفين — الفرونت بيسمح للمستوى 900 بكل الشاشات |
| 4. الحماية | `is_system = true` بمنع الحذف أو تعديل المستوى — قاعدة بيانات/باك إند (الشرط موثق هنا ومطبق في نموذج البيانات) |

## بوابات القمع (إلزامية لكل المستخدمين)

حسب معايير القبول، الشروط والإعداد إلزاميان **حتى لصانع النظام** — لأنهم بوابات UX مش فحوصات صلاحيات:

| الحالة | التوجيه |
|---|---|
| زائر + شاشة محمية | `/auth/sign-in` |
| مسجل + مش مقبل الشروط | `/terms` (زر القبول مقفول من غير checkbox) |
| قبول + مش مكتمل الإعداد | `/onboarding` (4 خطوات بالترتيب) |
| كامل + بيحاول يرجع لصفحات الدخول | `/dashboard` |
| رفض الشروط | تسجيل خروج كامل + مسح الجلسة |

## دورة الجلسة

- الجلسة (User DTO + حالة الشروط/الإعداد) محفوظة عبر Pinia persisted state — بتصمد بعد إعادة تشغيل التطبيق.
- «رفض وتسجيل الخروج» من شاشة الشروط أو «تسجيل الخروج» من قائمة المستخدم بينضّف كل الحالة ويرجّع لصفحة الدخول.
